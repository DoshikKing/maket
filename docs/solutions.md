# Модель решений и декомпозиции

## Концепция

Личное пространство содержит единое дерево сущностей. Решение объединяет проекты;
проект — объекты предметной области, папки и диаграммы. Декомпозиция — дочерние
сущности и диаграммы, раскрывающие содержимое выбранной сущности. Она доступна у
решения, проекта, объекта, связи, папки и диаграммы. Представление раскрывает
декомпозицию своей исходной сущности; независимая модель внутри визуальной копии
не создаётся.

| Сущность      | Хранение                                           | Представление на канвасе                        |
| ------------- | -------------------------------------------------- | ----------------------------------------------- |
| Решение       | ModelObject, kind=solution                         | Фигура выбранной нотации                        |
| Проект        | ModelObject, kind=project                          | Фигура выбранной нотации                        |
| Папка         | ModelObject, kind=folder                           | Организует дерево                               |
| Диаграмма     | Diagram + ModelObject, kind=diagram                | Содержит канвас                                 |
| Объект        | ModelObject, kind=object                           | Фигура выбранной нотации                        |
| Связь         | ModelRelation                                      | Стрелка выбранной нотации                       |
| Представление | Узел или ребро версионируемого документа диаграммы | Собственные геометрия, подпись, стиль и нотация |

Идентификатор сущности отличается от идентификатора представления. Для фигуры
ссылка — objectId, для стрелки — relationId. Одна сущность может иметь сколько
угодно представлений в рамках существующих лимитов документов, включая несколько
на одной диаграмме. Местоположение сущности в дереве не меняется при её размещении
на другом канвасе. Папка «Представления» — виртуальный индекс экземпляров с
ссылками `/diagrams/:id?element=:representationId`; она не содержит самостоятельных
копий объектов. Это системная дочерняя папка с постоянным идентификатором
`representations:<entityId>` и родителем-владельцем. Она создаётся автоматически
в дереве решения, проекта, объекта или связи, стоит первой среди дочерних
элементов и перемещается вместе с владельцем. Экземпляры внутри папки образуют
следующий уровень дерева; содержимое автоматически обновляется по ссылкам
objectId/relationId. Саму системную папку нельзя удалить или переместить отдельно,
в том числе когда она пуста. Представления удаляются с соответствующих диаграмм;
пока они существуют, сервер блокирует удаление владельца.

Нотация задаёт внешний вид и допустимые соединения, но не тип сущности и не
структурную вложенность. Один канвас сохраняет возможность подключить до 12
нотаций. Решение или проект можно разместить как любую совместимую фигуру, выбрав
их в дереве редактора. Связи могут соединять решения, проекты, объекты и другие
связи; их представления повторно используются на разных диаграммах.

## Вложенность и границы

- Решение находится в корне пространства или в корневых папках.
- Проект принадлежит решению, напрямую или через папки. Проекты не вкладываются
  друг в друга.
- Остальные сущности могут быть дочерними элементами друг друга. Диаграммы можно
  хранить на уровне решения, проекта, объекта, связи и в произвольных подпапках.
- Принадлежность проекту определяется ближайшим предком с kind=project. Изменение
  родителя переносит поддерево, не требует обновлять projectId у всех потомков.
- Объекты и связи личного пространства можно повторно представлять на диаграммах
  других уровней и проектов. Владение сущностью и её использование разделены.
  Новые объекты из палитры получают родителя контейнера текущей диаграммы.
- Запрещены циклы, чужие/отсутствующие родители и перемещение поддерева с проектом
  за пределы решения. Сервер проверяет эти ограничения под блокировкой ModelSpace.
- Сущность с дочерними элементами, участием в связях или представлениями нельзя
  удалить. Удаление диаграммы удаляет её представления и запись дерева, сохраняя
  исходные моделируемые сущности. Диаграмма с декомпозицией требует сначала
  переместить или удалить дочерние элементы.

Корневые объекты прежней модели остаются допустимыми для совместимости. Их можно
переместить в проекты через свойства или перетаскивание в обозревателе. Новое
пространство пустое: стандартные решения, проекты и моделируемые объекты не
создаются автоматически.

## Реализация и обновление

Миграция `20261008020000_solution_hierarchy` добавляет ModelObject.kind и
Diagram.entityId. Существующим диаграммам создаётся запись в корне дерева; их
канвасы, идентификаторы, история и публичные ссылки сохраняются. Диаграммы старого
формата получают запись дерева при штатном обновлении модели. Поле kind в JSON
необязательное: старые снимки и файлы продолжают трактоваться как обычные объекты.

Применение: `npm run db:migrate`, затем `npm run db:generate` и перезапуск приложения.
Миграция не создаёт искусственных решений/проектов и не меняет ранее применённые
миграции.

`GET /api/model/structure` возвращает типизированные сущности, краткий каталог
диаграмм и индекс представлений. Редактор получает только краткий каталог из
`GET /api/model`; раскрытие папки представлений загружает нужные диаграммы через
индекс использований (`GET /api/objects/:id/representations` или соответствующий
маршрут связей). Индекс представлений строится только для найденных диаграмм. Создание решения/проекта/папки использует
`POST /api/objects` с kind и parentId. Создание диаграммы — `POST /api/diagrams` с
parentId (идентификатор сущности, а не канваса). Изменения общей структуры и имени
проходят через API сущностей с проверкой revision/incarnation. Имя записи
диаграммы и канваса синхронизируется. Тип существующей сущности неизменяемый.

Дублирование диаграммы создаёт отдельную запись дерева в том же контейнере,
сохраняет ссылки на моделируемые сущности и не включает публичный доступ.
Экспорт/импорт одной диаграммы остаётся переносом канваса со снимками его объектов
и предков, а не экспортом решения целиком. Импорт создаёт независимые сущности;
включённые в снимок предки-диаграммы превращаются в папки, поскольку их канвасы
не входят в файл. Полноценный пакет решения с набором диаграмм — отдельный будущий
формат; текущий экспорт не заявляет такую возможность.

## Пользовательский сценарий

Открыть «Решения» → создать решение → создать внутри проект → создать папки и
объекты → выбрать объект → создать внутри диаграмму → открыть канвас → разместить
объекты, решение или проект из дерева. Кнопка «Декомпозиция» возвращает в выбранную
ветку. Папка «Представления» позволяет открыть конкретный экземпляр на нужной
диаграмме. «Библиотека» сохраняется как общий список всех канвасов.
